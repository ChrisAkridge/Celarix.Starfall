# Chart Performance and Bulk Data Plan

## Purpose

Create deterministic, repeatable scaling scenarios for practical chart workloads before implementing caches, hierarchical summaries, pooling, or interactive-quality reductions.

The expected upper working set is initially approximately 100,000 to 1,000,000 visible or query-relevant observations. Astronomical generated domains should remain bounded by the function sampling budget but are not expected to provide rigorous population statistics.

## Benchmark Harness

Use BenchmarkDotNet for repeatable micro- and component-level measurements. Keep the benchmark project separate from unit tests so normal development and CI test runs remain fast.

The benchmark project should:

- Reference `Celarix.Starfall` directly.
- Use deterministic generated data and fixed random seeds.
- Run optimized builds through BenchmarkDotNet's normal process isolation.
- Report execution time, operations per second where meaningful, allocated bytes, and garbage collections.
- Parameterize observation count and scenario type.
- Avoid console logging inside measured operations.
- Separate one-time setup from the operation being measured.
- Retain benchmark results or summarized baselines in a human-readable form when conducting a performance review.

Do not initially establish pass/fail performance gates. First collect scaling behavior and identify dominant costs.

## Scaling Sizes

Use at least:

```text
10,000 observations
100,000 observations
1,000,000 observations
```

Smaller diagnostic sizes may be added to expose fixed overhead. Larger sizes should be added only if the million-point case remains inexpensive and memory permits.

## Deterministic Synthetic Data

### Dense Linear

```text
X = 0..N-1
Y = X
```

Purpose: simple ingestion, exact expected extrema, continuously distinct sorted values, and predictable bucket averages.

### Large Offset with Small Variation

```text
Y = 1e12 + sin(X / scale)
```

Purpose: numerical stability for Welford, recalculation, and stable bucket means.

### Repeated Values

```text
Y = X mod smallCardinality
```

Purpose: sorted-frequency index behavior, modes, percentiles, and memory behavior when Y cardinality is small.

### Deterministic Trend and Noise

```text
Y = trend(X) + seededNoise(X)
```

Purpose: realistic-looking variation with reproducible results.

Noise should be generated by a fixed seed or stable X-derived hash so benchmark setup is deterministic.

### Weather-Like Series

Combine:

- Seasonal cycle.
- Daily cycle where the X resolution supports it.
- Station-specific offset.
- Slow trend.
- Deterministic noise.
- Missing/null observations.
- Occasional deterministic outliers.

Purpose: approximate NOAA-style temperature or measurement behavior before real records are available.

For multiple stations, either construct separate series or encode station selection before building the measured series. Do not overload the one-dimensional X model merely to make benchmark generation convenient.

### Calorie-Like Series

Generate daily observations with:

- Weekday/weekend patterns.
- Slow goal or behavior changes.
- Missing days.
- Occasional high-calorie outliers.

Purpose: scale up the existing playground concept while preserving a recognizable application shape.

### Sparse Huge-X Series

Store a moderate number of points whose X values are separated by enormous `BigInteger` gaps.

Purpose: verify that ordered range query cost depends on stored/matching observations rather than numeric width.

This scenario should primarily benchmark range lookup and resolution, not attempt to materialize the implied domain.

### Generated Function Domain

Use deterministic functions over very large `BigInteger` ranges with a fixed bucket count and samples-per-bucket.

Purpose: confirm that work remains bounded by requested output resolution rather than domain cardinality.

Include smooth, periodic, and deliberately alias-prone functions, while treating aliasing as a quality observation rather than a performance failure.

## Benchmark Groups

### Series Construction

Measure:

- Creating a `DataSeries` from a prepared point sequence.
- Building statistical and ordered indexes.
- Peak or reported managed allocations.

Keep point generation outside the measured operation unless a separate ingestion benchmark intentionally includes it.

### Incremental Mutation

Measure batches of deterministic:

- Additions.
- Removals.
- Numeric replacements.
- Numeric/null transitions.

Report per-operation scaling and verify the benchmark does not accidentally measure event subscribers or console warnings unless that is the scenario's purpose.

### Full Statistics Recalculation

Measure `RecalculateStatistics()` across all standard sizes and data shapes.

Compare incremental and rebuilt results outside the timed portion when correctness verification is desired.

### Ordered Range Queries

Measure:

- Small window over dense data.
- Large window over dense data.
- Empty window.
- Window over sparse huge-X data.
- Slowly moving windows if a sequence benchmark is useful.

Parameterize the fraction of stored observations matched by the query.

### Data Resolution

Measure exact stored-series resolution at representative bucket counts such as:

```text
640
1280
1920
3840
```

Record how cost scales with total observations, matching observations, and bucket count.

Measure function-source resolution separately with samples-per-bucket parameters.

### Renderable Construction

Measure transformation of resolved buckets into bar renderables without actual drawing when it can be isolated cleanly.

This helps distinguish data-resolution cost from geometry and color construction.

### Full Offscreen Frame

Use an offscreen render target to measure a complete chart frame where feasible:

- Static frame after invalidation.
- Repeated unchanged frame.
- Viewport-changing frame.
- Data-changing frame.

This is closer to an integration benchmark and may be noisier than the component benchmarks. Keep the component measurements as the primary diagnostic tools.

## Interactive and Offline Scenarios

Before a formal global rendering policy exists, emulate the two intended workloads through benchmark parameters:

### Interactive-Like

- Repeated viewport changes.
- Standard display resolution.
- Current sampling budget.
- Many consecutive invalidations.

### Offline/Video-Like

- Explicit full statistics recalculation before the measured render sequence when desired.
- Higher display resolution or sampling budget.
- Deterministic repeated runs.
- Emphasis on final quality and stable output rather than frame deadline.

Do not optimize the interactive path at the expense of deterministic offline semantics without an explicit future policy decision.

## Instrumentation Outside BenchmarkDotNet

Some pipeline measurements may be easier to understand with optional internal timing around:

- Source resolution.
- Label measurement and fitting.
- Geometry/renderable construction.
- Drawing.

Use this instrumentation for whole-frame attribution, while BenchmarkDotNet measures isolated operations and allocations. Avoid permanently noisy console output; diagnostics should be opt-in or returned as structured timing data.

## Interpretation

Look first for scaling shape rather than a single machine-specific number:

- Does a tenfold data increase produce roughly tenfold work where expected?
- Does sparse range lookup remain independent of numeric X width?
- Does function resolution remain bounded by buckets and samples?
- Which stage dominates invalidated frames?
- Are allocations proportional to observations, buckets, or both?
- Is repeated unchanged rendering substantially cheaper than invalidated rendering?

Only schedule caching, pooling, hierarchical summaries, or invalidation-level refinement after a benchmark identifies the actual bottleneck.

## Real Data Later

Synthetic data is sufficient for implementation and initial scaling analysis. Real NOAA data should later validate:

- Irregular timestamps.
- Missing and duplicated observations.
- Multiple station timelines.
- Realistic value distributions and outliers.
- Import and filtering ergonomics.

Real data complements deterministic benchmarks; it does not replace them.
